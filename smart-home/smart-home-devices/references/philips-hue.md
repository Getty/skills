# Philips Hue / Signify

Research baseline 2026-10-22. Hue is a Zigbee-first system: lamps and accessories mesh on Zigbee to a bridge. Bluetooth (2019+ lamps) and Matter-over-Thread (2025+ lamps) were added beside it. Under every alternative route, check which features you give up before leaving the bridge.

## Identify the line from the label or model ID

- **Zigbee manufacturer:** `Philips` (older) or `Signify Netherlands B.V.` (newer) ([ZHA quirks](https://github.com/zigpy/zha-device-handlers/blob/dev/zhaquirks/philips/__init__.py)). Zigbee manufacturer code `0x100B`.
- **modelID prefix** (pattern seen in [Z2M philips.ts](https://github.com/Koenkk/zigbee-herdsman-converters/blob/master/src/devices/philips.ts)): `L` = light, `R` = remote/switch module, `S` = sensor (`SML` motion, `SOC` contact), `LOM` = plug or wired switch, `COM` = siren/chime. Second letter on lights: `C` = White and Color Ambiance, `T` = White Ambiance, `W` = White, `L`/`H` = legacy LivingColors-era luminaires. Third letter usually gives the form: `A` = A-shape (BT-era `LCA`/`LTA`/`LWA`), `G` = spot, `E` = candle, `B` = BR30, `L` = strip, `X` = gradient strip or string, `D` = downlight, `O` = globe, `V` = Edison. Treat the decode as a hint and look up the exact ID.
- **Generation:** `LCT001–LCT016`, `LTW…` and `LWB…` are pre-Bluetooth bulbs. Z2M descriptions marked "with Bluetooth" and the Bluetooth logo on the box mean BLE-capable (2019+). Some 2024+ products report a 12NC as their modelID (`929004…`), not a letter code.
- **Product codes:** 12NC material numbers `929…`/`9290…`. EANs seen in definitions begin `8718696`, `8719514` or `8720169` (EU) or UPC `046677` (US).
- **Bridge:** `modelid` `BSB002` = v2, `BSB003` = Bridge Pro (HA code). `BSB001` is reported for v1.
- **Packaging and labels:** the Matter logo, the QR code in the guide and an 11-digit code on the bulb mark direct-Matter lamps ([Hue Matter guide](https://www.philips-hue.com/en-us/support/article/philips-hue-and-matter-complete-setup-and-support-guide/000012)). "Works with Hue" marks a third-party Zigbee device. The 6-hex serial printed on the lamp is used for Touchlink reset.

## Choose the route

- **Bridge + `hue` (default):** lights, rooms/zones (grouped lights disabled by default), scene entities with a Scene select per room/zone, remotes as `hue_event` + `event` entities, motion/lux/temperature, contact/tamper, MotionAware, behavior enable switches, and a Zigbee connectivity sensor. On V2, the option "ignore connectivity" keeps sleeping remotes from showing as unavailable. HA cannot edit scenes. Prefer Hue scenes for multi-lamp changes: the bridge batches them.
- **Direct Zigbee (Z2M/ZHA):** choose this only for a concrete need, such as removing the bridge, a mixed mesh, or exposure the bridge does not give. You lose Hue scenes, gradient segments, entertainment and MotionAware. Reset lamps with Touchlink by serial: Z2M frontend → Touchlink → Philips Hue reset, or the `philips_hue_factory_reset` action. A community-sourced power-cycle reset also exists: 5× off 2 s / on 8 s ([Z2M device page](https://www.zigbee2mqtt.io/devices/9290012573A.html)). Z2M's OTA index carries Signify images for some models; check each model.
- **Hue BLE (`hue_ble`, HA 2025.12):** one lamp per BLE link. Make the lamp discoverable through Hue app → Voice Assistants, or factory-reset it; a reset changes the BLE address. Only the adapter or proxy used at setup controls it. The integration does not reconnect after a long outage. No mesh, no bridge scenes ([HA Hue BLE](https://www.home-assistant.io/integrations/hue_ble/)). Products on BLE cannot join Matter.
- **Matter-over-Thread (2025+ lamps):** HA Matter + a Thread border router. A lamp chooses Zigbee or Thread at commissioning. Signify announced a concurrent Zigbee+Thread update for "later this year" (2026) on MG26/SiMG301-based bulbs ([Silicon Labs](https://news.silabs.com/2026-06-23-Signify-Enhances-Philips-Hue-Matter-Support-Through-Collaboration-with-Silicon-Labs)). Remove the lamp from the bridge before direct Matter pairing. While a lamp is registered to a bridge, Thread stays disabled (interview report). Direct Matter loses gradient, dynamic scenes and entertainment.

## Assess an existing installation

Count physical devices separately from logical groups. Rooms, zones and entertainment areas are not radios. Keep the bridge while scenes, updates, remotes and household use work. Before moving any device, compare against the exact Z2M/ZHA definition.

For each room, name the scene owner. When Hue scenes, Adaptive Lighting, wall-switch behavior and presence automations all touch the same lamps, define a priority and a manual-override period. A failed transition can come from competing commands, wall power cut, bridge connectivity or the lamp's radio path. These are distinct faults. A group's state can mean "any on"; it does not prove every lamp got the command.

## API and diagnostics

V1 resources are legacy. CLIP v2 adds the event stream (MotionAware, contact, camera motion, behavior and entertainment resources). Authorize against the real bridge and keep application keys out of logs ([developer onboarding](https://developers.meethue.com/develop/get-started-2/)). Prefer the HA integration over a second poller. For read-only investigation, record bridge software and API generation, then compare one resource with its HA entity. Diagnose in layers: power and vendor app → bridge reachability → integration log/event stream → entity → automation trace. "Unavailable" is not "off"; never toggle on a transient unavailable.

## Evidence and acceptance

A 2025-10-09 report (HA 2025.10.1, Bridge Pro) described temporary unavailability and lights switching. Moving the bridge's network link did not fix it, and the issue closed stale ([core #154049](https://github.com/home-assistant/core/issues/154049)). Correlate history, power and logs; it is not evidence that Hue bridges fail generally. Reports conflict on whether Essential lamps have Thread; Signify's release says they do. Verify the box marks.

Acceptance: every remote event, motion/lux/temperature, a room scene, power restoration, HA restart, bridge restart and manual override. Record each feature lost under Matter, BLE or direct Zigbee before changing the route.
